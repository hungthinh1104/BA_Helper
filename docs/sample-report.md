## 3. Detailed Evidence

### `BookingController.cancelBooking`
**Extracted Context:**
```typescript
@Post(':id/cancel')
async cancelBooking(@Param('id') id: string) {
  return this.bookingService.cancel(id);
}
```
**Impact Note:** The controller currently only delegates to `cancel`. It needs to be updated to accept a `reason` payload and perhaps explicitly return a refund status object to the frontend.

### `RefundService.processRefund`
**Extracted Context:**
```typescript
async processRefund(transactionId: string, amount: number) {
  // Initiates communication with payment provider API
  return this.paymentGateway.refund(transactionId, amount);
}
```
**Impact Note:** This service already exists for administrative refunds but needs to be securely exposed to the user-initiated cancellation flow. We must ensure idempotency to prevent double refunds.

## 4. Unknowns & BA Questions

## 5. QA Scenarios & Risks

1. **Idempotency Risk:** A user rapidly clicking the "Cancel" button might trigger multiple concurrent refund requests to the payment gateway.
   - *Test Scenario:* Simulate concurrent API calls to `/cancel` and ensure only exactly one refund is processed.
2. **State Machine Bypass:** Ensure a booking already in `COMPLETED` or `IN_PROGRESS` state cannot be transitioned back to `CANCELLED_REFUNDED`.
   - *Test Scenario:* Attempt to cancel a booking where the event date is in the past. Expect a `400 Bad Request`.
3. **Partial Refunds:** If a booking is cancelled within 24 hours of the event, the business rules might dictate only a 50% refund.
   - *Test Scenario:* Cancel a booking 12 hours before the start time and assert that the refund amount is exactly 50% of the original transaction.
